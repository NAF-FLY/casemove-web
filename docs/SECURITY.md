# SECURITY.md — Безопасность и работа с данными в Casemove Web

Этот документ описывает подходы к безопасности в проекте Casemove Web: хранение секретов, работу с Steam-аккаунтами, мультиюзерность и ограничения для операций.

---

## 1. Общие принципы

1. **Все чувствительные данные живут только на backend.**
2. **Frontend никогда не получает и не логирует Steam-креды, токены, секреты.**
3. Backend — единственная точка доступа к Steam/CS2 Game Coordinator.
4. Архитектура сразу готовится под мультиюзерность, но MVP может работать с одним аккаунтом.

---

## 2. Секреты и переменные окружения (MVP)

На этапе MVP проект работает с **одним Steam-аккаунтом**, заданным через ENV:

Примеры переменных окружения (названия условные):

- `STEAM_USERNAME`
- `STEAM_PASSWORD`
- `STEAM_SHARED_SECRET`
- `STEAM_ID`
- `ENCRYPTION_KEY` (может появиться уже на MVP для шифрования временных токенов)

Требования:

- ENV-файлы (`.env`) не коммитятся (`.gitignore` обязательно).
- Логика чтения ENV инкапсулируется в модуле конфигурации backend (например, `apps/api/src/plugins/config.ts`).
- Значения переменных не выводятся в логах (даже в debug-режиме).

---

## 3. Хранение Steam-кредов (мультиюзерный режим)

В будущем, когда появятся реальные пользователи и возможность привязать их Steam-аккаунты, вводятся сущности:

```ts
type User = {
  id: string;
  email?: string;
  nickname?: string;
  createdAt: Date;
};

type SteamAccount = {
  id: string;
  userId: string;
  steamId: string;
  displayName?: string;
  encryptedCredentials: string; // шифрованный JSON с токенами/секретами
  createdAt: Date;
  updatedAt: Date;
};
```

### 3.1. encryptedCredentials

Поле `encryptedCredentials` хранит зашифрованный JSON, в котором могут быть:

- refresh-токены
- session-токены
- shared secret / доп. данные, необходимые для автоматизации

Шифрование:

- используется симметричный ключ `ENCRYPTION_KEY` из ENV
- логика шифрования/дешифрования вынесена в `core/security.ts` на backend
- расшифровка происходит **только в памяти**, перед созданием `SteamClient`

Никаких открытых Steam-паролей/логинов в БД.

---

## 4. Доступ к Steam — только через SteamClient / SteamManager

**Запрещено:**
- вызывать `steam-user` / `globaloffensive` напрямую из HTTP-роутов или WebSocket-обработчиков;
- использовать эти библиотеки на frontend (невозможно и небезопасно).

**Разрешено и обязательно:**
- создать `SteamManager` (core слой), который управляет набором `SteamClient` по `steamAccountId`;
- `SteamClient` внутри инкапсулирует:
  - логин;
  - поддержание соединения;
  - запросы инвентаря;
  - операции над Storage Units;
  - обработку ошибок, reconnect, ретраи.

Это важно для безопасности, централизованного контроля и возможности ограничивать операции.

## 5. Аутентификация и авторизация (фаза 2)

### 5.1. Auth frontend → backend

После внедрения мультиюзера frontend должен:

- использовать auth-слой (например, Auth.js / NextAuth) с провайдером Steam или другим логином;
- получать идентификатор пользователя (`userId`);
- прокидывать в запросы к backend токен (JWT или подписанный access-token).

### 5.2. Auth backend

На backend добавляется Fastify-плагин `auth.ts`, который:

- проверяет токен (подпись, срок действия, audience/issuer);
- при успешной валидации добавляет `request.user` с `userId` (и, возможно, `steamAccountId`);
- отклоняет запросы без валидного токена (кроме публичных эндпоинтов, например `/health`).

Все модули (`inventory`, `storage`, `bulk`) должны работать **в контексте пользователя**, а не глобального аккаунта.

## 6. Ограничения и защита от абузов

Чтобы не допустить злоупотребления сервисом (DoS/спам, резкие пики активности, риск блокировки у Steam), вводятся ограничения.

### 6.1. Rate limiting

На уровне Fastify или отдельного middleware:

- ограничение количества запросов на IP / токен за единицу времени;
- отдельные жёсткие лимиты на:
  - `POST /bulk-move`
  - trigger-операции, которые меняют инвентарь.

### 6.2. Лимиты задач

На уровне бизнес-логики bulk-очереди:

- ограничение **количества одновременно активных задач** `BulkMoveTask` на одного пользователя;
- ограничение **размера одной задачи**:
  - максимум предметов в одном bulk-запуске;
  - ограничение частоты запусков (cooldown между большими операциями).

### 6.3. Логирование

Логируем только:

- техническую информацию (id задачи, статус, ошибки на уровне бизнес-логики);
- информацию об ошибках Steam в обобщённом виде (без сырых кредов или токенов).

Не логируем:

- ENV-переменные;
- содержимое `encryptedCredentials` до/после дешифрации;
- полные raw-ответы с чувствительными данными.

---

## 7. WebSocket и безопасность

- WebSocket-подключения должны быть привязаны к авторизованным пользователям (в мультиюзерном режиме).
- Подписки на события (`bulkMoveProgress`, `bulkMoveDone`) привязаны к `taskId` **и** `userId`.
- Пользователь не может:
  - подписаться на чужой `taskId`;
  - получать события задач других пользователей.

Это должно обрабатываться либо в WS-слое, либо в middleware для событий.

---

## 8. Разработка и debug

При локальной разработке допускается:

- расширенный лог (но без секретов);
- работа с одним локальным Steam-аккаунтом через `.env`.

Нельзя:

- коммитить `.env`;
- выкладывать логи с реальными кредами/ID в публичные места;
- использовать продовые креды в dev-окружении без строгой необходимости.

---

## 9. Краткое резюме

1. Все чувствительные данные (Steam креды, токены, secrets) — только на backend и только в зашифрованном виде при хранении.
2. Взаимодействие со Steam — строго через `SteamManager`/`SteamClient`.
3. REST и WebSocket работают **от имени пользователя**, а не глобального аккаунта.
4. Ограничения (rate limiting, лимиты задач) обязательны для защиты сервиса и аккаунтов.
5. Любые изменения, касающиеся безопасности, должны быть согласованы и отражены в этом файле и в архитектурной документации.
